# 미팅용 한눈에 보기

> **문서 갱신 (2026-10):** 아래 본문 중 초기 미팅 시점 문장은 그대로 두되,  
> **현재 웹에는 수동 합차·카카오 지도/경로·BOX별 중량이 반영됨.**  
> 아직 없는 것: 합차 1set **강제** 자동 묶음, 통행료·유류비 최적화, AI 배차, 앱.

## 현재 만든 것의 위치

**업무 방향 확인용 일일 배차 프로토타입** (확정안·ERP 아님)

> 어디에(지역) + 얼마나(수량) → 차 추천 → 그날 일정에 쌓기

하는 일: 등록·추천·수정·완료·엑셀 가져오기/내보내기, 박스→PLT·중량, **수동 합차**, **경로·지도**  
안 한 것: 합차 1set 강제, 통행료·유류비 최적화, AI 최적 배차, 용차 강제, 제품/거래처 ERP

현재 구현은 한 가지 업무 가설을 화면으로 만든 것이다. 이 방식으로 간다는 결정도, 기존 엑셀보다 효율적이라는 검증도 아직 끝나지 않았다.

## 기간과 현실적인 범위

**11월부터 12월 셋째 주까지 약 7주.**  
이 기간에 전체 물류시스템을 운영 수준으로 구축하는 것은 어렵다.  
현실적인 목표는 업무 분석, 핵심 기능 프로토타입, 효과 검증과 인수인계 자료다.

실제 운영을 원하면 종료 후 서버·데이터·오류·규칙 변경을 맡을 사내 담당자 또는 외부 유지보수 주체가 먼저 정해져야 한다.

## 미팅에서의 역할

먼저 듣기 → **실제 문제 / 필요한 결과 / 운영 책임**을 확인하기.  
그다음 **현재 확인 가능 / 규칙이 필요 / 후속 구축**으로 나누기. 즉석 약속하지 않기.

| 들으면 | 판단 |

| 일정 등록·지역·수량·추천·엑셀 | 현재 프로토타입으로 확인 가능 |
| PLT 표, 차 한도, 지역 구분 | 현장 기준을 받아 검증 필요 |

## 앱까지 붙이면 (웹보다 더 걸림)

지금 만든 것은 **브라우저용 웹**이다.  
별도 앱이 같은 일정을 읽고·쓰려면 아래가 추가로 필요하다.

1. **API** — 지금 등록·수정은 웹 폼/서버 액션 중심. 앱용으로 일정 조회·등록·차 변경 API를 따로 열어야 함
2. **앱 화면** — 날짜 목록·등록·차 선택 등 (조회만인지, 등록·배차까지인지에 따라 기간이 갈림)
3. **배포** — 폰은 `localhost`에 못 붙음. 서버·HTTPS·누가 쓰는지(권한)

| 범위 | 감 |
| --- | --- |
| 웹에서 지역·수량·추천 검증 | 현재 7주 안에서의 현실적 목표 |
| + 앱이 웹과 같은 일정 읽고/쓰기 | **그보다 몇 주~개월 추가** |
| + 지도·경로·AI | 또 크게 늘어남 |

앱이 나와도 “화면만”이 아니라 **통신 길(API) + 배포**가 같이 붙는다.
