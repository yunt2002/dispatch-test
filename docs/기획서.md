# 네오마그네틱 배차 — 기획서

작성: 2026-09-16  
상태: **방향 검토용 프로토타입** (구현 기능은 있으나 운영 방향·효율은 미확정)  
사람용 기능 확인 방법은 [사용설명서.md](./사용설명서.md) 입니다.

> 이 문서는 현재 구현된 가설과 기능 범위를 설명한다.  
> 현재 방식으로 실제 운영 시스템을 구축하기로 확정된 것은 아니며, 현업 미팅을 통해 문제·효율·운영 주체를 먼저 검증한다.

---

## 1. 왜 만드는가

매일 납품 일정을 엑셀에서 보고, 지역과 수량을 보고, 어느 차를 보낼지 정한다.  
엑셀을 복제하는 화면이 아니라, **그날 넣을 건을 바로 넣고 차가 추천되는 도구**가 필요하다.

엑셀은 이미 쓰는 `납품예상 일정표 및 납품관리` 양식이 있다.  
그 파일을 **처음 가져오고**, 나중에 **같은 양식으로 다시 내보내는 것**만 엑셀로 한다.

---

## 2. 현재 검증 중인 가설

**지역 + 수량 → 차량 추천 → 그날 일정에 쌓기**

추천은 제안이다. 담당자가 다른 차로 바꿀 수 있다.

다만 차량 선택 자체가 현업의 핵심 병목인지 아직 확인되지 않았다. 일정 취합, 반복 입력, 합차 판단, 변경 공유 또는 배차표 작성이 더 큰 문제라면 개발 방향은 달라질 수 있다.

---

## 3. 하지 않는 것 (ERP가 아니다)

처음부터 범위를 이렇게 잘랐다. 마스터를 키우면 ERP처럼 보이고, 매일 쓰는 속도가 죽는다.

| 하지 않음 | 이유 |
| --- | --- |
| 제품·거래처 마스터 관리 | 일정 행에 이름만 있으면 된다 |
| 합차 (여러 행을 한 대에 묶기) | 물류 규칙이 아직 없다 |
| 표에 없는 품목을 박스÷임의수 = PLT | 틀린 숫자가 확정처럼 보인다 |
| 용차·택배를 자사 차로 강제 | 현장 분류를 코드가 덮으면 안 된다 |
| 파렛트 mm으로 차 고르기 | 지금은 박스→PLT 개수만 확정 |
| 예전 출하·루트·로그 화면 | 일정 홈이 본체 |

---

## 4. 현재 프로토타입에 구현된 것

아래 흐름은 기능 확인이 가능한 상태다. 실제 업무 효율과 운영 적합성이 검증됐다는 의미는 아니다.

1. 기존 엑셀을 **처음 한 번** 가져온다. (`source=EXCEL`)
2. 홈에서 납품일·지역·수량·(선택)품명·거래처를 넣고 **즉시 추천**한다. (`source=MANUAL`)
3. 그날 목록에서 차를 바꾸고, 수정하고, 완료/취소하고, 삭제한다.
4. **이 달** 또는 **전체 시트**로 원본 양식 엑셀을 내보낸다.
5. 품명/품번이 제품군 표와 맞으면 **입수(박스/PLT)** 로 PLT를 계산한다.

### 화면

- **일정 · 배차** — 매일 쓰는 홈. 내보내기만 헤더에 둔다.
- **설정 → 처음 가져오기 / 차량 / 지역**
- 예전 메뉴(출하, 제품, 거래처, 적재, 로그 등)는 홈으로 보낸다.

### 일정 행에서 되는 일

- 차량 변경: PLT가 있으면 대수(`×N`)를 다시 계산
- 수정: 지역·거래처·품명·수량. 지역/수량/품명이 바뀌면 추천을 다시 돌림
- 완료 / 완료 취소 / 삭제(확인)
- 목록 순서: 지역 → 거래처 → 품명
- 날짜: 일정이 있는 날 목록 + 빈 날로 가는 날짜 칸 (`9/16(수)`)

### 엑셀

- 가져오기: 월 시트(비우면 최근 월). 다시 올리면 **엑셀에서 온 행만** 교체. 직접 등록은 유지. 건수 있으면 확인.
- 내보내기: 이 달(시트 하나) / 전체 시트(월별 시트). 날짜 `9/16(수)`.

---

## 5. 추천 규칙

순서대로다.

1. **지역** — 수도권 → 2호차, 지방 → 1호차. 미등록 위치는 미분류, 차는 추천하되 지역 목록에 자동 저장하지 않음.
2. **PLT를 알면** — 차량 PLT 한도로 대수.
3. **박스 + 품명이 표에 있으면** — 입수로 PLT를 구한 뒤 2번. 홈에서 품명을 넣거나, 엑셀 행에 품명이 있을 때.
4. **박스만 있고 표에 없으면** — PLT를 만들지 않음. 지역 추천만.

추천과 실제 선택이 다르면 행에 원래 추천이 남는다.

홈 오른쪽 `1호차 4건 · 2호차 5건`은 **행 개수**다. 합차가 아니다.

---

## 6. 적재·차량 (현장 표 + 잠정)

### 입수 (2026-10 현장표 반영)

입수 = 1PLT당 박스. P 접이식박스 = P 박스. 낱개(TMED2, GEN1, EC PUMP)는 PLT 환산 없음.

수출/CE는 수출 행을 먼저 본다. 예: `SBW ROTOR ASSY (CE)` → DIC(수출) 30박스/PLT.  
`3.2 ROTOR` / HFP3.2는 입수 60. 파렛트 규격은 스펙 기록용이며, **치수로 차 추천은 아직 안 함.**

**제품별 중량은 미수령.** 잠정 700kg/PLT만 있음.

박스 종류: P(이삿집)·종이(택배)·단프라(플라스틱 공박스).

### 차량 (잠정, 설정에서 수정)

| 차량 | 톤 | 적재함 | 계산용 PLT | 용도 |
| --- | --- | --- | --- | --- |
| 1호차 | 4.0t | 5,200×2,300 | 8 | 지방. 계산은 8PLT |
| 2호차 | 3.5t | 5,000×2,150 | 8 | 수도권 |
| 3호차 | 2.5t | 미정 | 2 | 긴급 |
| 스타리아 | 1.0t | 미정 | 1 | 긴급·소량 |

적재함 치수는 기록됨. **파렛트 규격×적재함으로 몇 PLT인지 계산하는 로직은 아직 없음.**

충청 일부(음성, 충주, 청주, 서산, 예산 등)를 수도권으로 둔 것도 잠정이다.

### 2026-10-28 반영

- **600kg/PLT** 기준 (설정·시드)
- 1·2호 **윙바디 · 최대 8 PLT** 제원 통일 + 적재함 치수 기록
- 제품군 → **납품고객사** 매핑
- **고정 권역 루트 마스터** (전라도·경상도 → 1호, 충청/세종 유동 → 잔여 PLT)
- 홈 **잔여 PLT** 표시, 낱개 박스는 PLT 합산에서 제외·별도 안내
- Geocoding/거리·통행료: `src/lib/geocoding.ts` 골격 (카카오 키 있으면 주소 좌표). **도로거리·통행료 자동 산출은 API 연동 후**

### 아직 없는 것 (TO BE)

- 왕복 km·통행료·유류비 종합 최적화 (지도 API + 요금표)
- 적재함 mm × 파렛트 mm으로 PLT 장수 재산정
- 전라도 BMC+코아 등 **합차 1set** 강제 묶음

## 7. 데이터 원칙

진짜 원본은 **일정 한 줄(`ScheduleEntry`)** 이다.

- `MANUAL` — 홈에서 직접 넣음
- `EXCEL` — 엑셀에서 가져옴. 재가져오기 때 이 것만 교체

제품/거래처/출하/루트 테이블은 초기에 ERP처럼 만들다 남은 것이다. **새 기능은 일정 쪽에만 둔다.**

- 700kg/PLT 확정

## 9. 앱·API (웹보다 추가 기간)

현재 결과물은 **브라우저용 웹**이다. 등록·수정·추천은 웹 폼/서버 액션 중심이라, 앱이 같은 데이터를 쓰려면 길이 더 필요하다.

앱이 웹과 통신하려면:

1. **API** — 일정 조회·등록·차 변경 등을 앱이 호출할 수 있게 따로 연다
2. **앱 화면** — 조회만인지, 등록·배차까지인지에 따라 범위가 갈린다
3. **배포** — 폰은 `localhost`에 붙지 않는다. 서버·HTTPS·권한·유지보수가 필요하다

| 범위 | 기간 감 |
| --- | --- |
| 웹 프로토타입으로 업무 검증 | 약 7주 안의 현실적 목표 |
| + 앱 ↔ 웹 같은 일정 읽고/쓰기 | **그보다 몇 주~개월 추가** |
| + 지도·경로·AI | 또 크게 늘어남 |

“간단한 앱”이라도 화면만 만드는 시간이 아니다. **통신(API) + 배포**가 같이 붙는다.  
7주 안에는 웹 검증이 우선이고, 앱은 별도 구축 범위로 둔다.

## 10. 기술 (담당자)

- Next.js 16 + React 19, Prisma, SQLite
- 실행: `npm run dev` → `http://localhost:3000`
- `npm run db:seed` 는 차량·지역을 다시 심는다. **이미 쓰는 일정을 지울 수 있다.**

핵심 파일:

- `src/app/page.tsx` — 홈
- `src/app/schedule/actions.ts` — 등록·수정·차 변경·완료·삭제
- `src/lib/dispatch-group.ts` — 추천·대수
- `src/lib/product-loading.ts` — 제품군 적재표
- `src/lib/import-schedule.ts`, `src/lib/delivery-export.ts` — 엑셀

앱을 붙일 때는 위 로직을 호출하는 **API 계층**을 새로 두는 편이 맞다. 지금 화면을 그대로 앱에 붙이기는 어렵다.

## 11. 프로토타입 검증 기준

- 엑셀 없이 지역·수량만으로 그날 일정을 넣을 수 있다.
- 품명을 넣으면 표에 있는 제품은 `64 박스 · 2 PLT`처럼 보인다.
- 추천을 무시하고 다른 차로 바꿀 수 있다.
- 엑셀을 한 번 가져오고, 같은 양식으로 이 달/전체 시트를 다시 뺄 수 있다.
- 화면이 ERP 마스터 관리처럼 보이지 않는다.

위 항목은 구현 확인 기준이다. 실제 성공 여부는 기존 엑셀 대비 시간 절감, 오류 감소, 반복 입력 감소 등 현업 효과를 별도로 확인해야 한다.

## 12. 운영 전제와 기간

2026년 11월부터 12월 셋째 주까지는 약 7주다. 이 기간에 전체 물류시스템·앱·지도 배차까지 운영 수준으로 구축하는 것은 범위와 유지보수 측면에서 현실적이지 않다.

이 기간의 현실적인 결과물은 다음 중 하나다.

1. 현행 업무 분석과 핵심 기능 검증용 **웹** 프로토타입
2. 기존 엑셀 흐름을 유지하는 제한적 자동화
3. 범위를 매우 좁힌 업무 도구와 인수인계 자료

앱·지도·운영 투입을 원하면 그다음에 다음이 정해져야 한다.

- 사내 또는 외부 유지보수 담당자
- 서버·계정·권한 관리 주체
- 데이터 백업과 복구 방법
- 장애 발생 시 기존 엑셀로 돌아가는 절차
- 엑셀 양식과 현장 규칙 변경 시 수정 책임
- (앱이면) API·배포·앱 수정 책임

유지보수 주체가 없다면 업무가 시스템에 의존하도록 만들지 않는다.
